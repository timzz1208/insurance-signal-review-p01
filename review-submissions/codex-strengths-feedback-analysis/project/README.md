# 別急著補短板，先找出你的超預期

IG `@timzz1208`｜觀念型、可收藏、不推銷

本資料夾是以繁體中文、教育部標準字形（芫荽 Iansui）製作的手繪線稿 Reels 與 4:5 輪播。內容把「德魯克回饋分析法」改寫成一個低門檻的自我觀察練習：不要只問自己哪裡不夠好，先留下「預期／實際」紀錄，再從多筆結果找出可重複的能力線索。

## 交付物

- `output/strengths_feedback_analysis.srt`：與影片燒錄字幕同一套時間軸。

- `render/`、`tools/`：可重跑的渲染與音訊產線。

## 旁白稿

每句一行、每句控制在 30 字內；成品時間以實際 TTS 波形為準。

> 你一直在補短板，卻可能補錯了地方。<br>
> 先問一個更有用的問題：<br>
> 什麼事，你總是做得比預期好？<br>
> 很多人只記得哪裡不夠好。<br>
> 但自我評估本來就不一定準。<br>
> 只靠感覺，很難看見自己的強項。<br>
> 德魯克提出一個簡單的方法：<br>
> 重要行動前，寫下你預期的結果。<br>
> 之後再把實際結果，拿回來對照。<br>
> 不要被一次成功說服，也不要被一次失敗定型。<br>
> 把幾次紀錄放在一起，看重複出現的模式。<br>
> 哪些任務、情境、做法，常常超出預期？<br>
> 強項不是自我感覺良好。<br>
> 它是被結果反覆驗證的能力線索。<br>
> 下一次，先把時間放到這條線索上。<br>
> 不是放棄短板，而是先找到你的高槓桿。<br>
> 收藏這套問題，下一次行動前拿出來。

## 事實查證表

| 成品主張／設計 | 判定 | 採用依據與限制 |
|---|---|---|
| 重要行動前記下預期，之後比較實際結果 | **可採用** | Peter F. Drucker〈Managing Oneself〉：HBR 1999 原文／2005 `Best of HBR` 重刊都把 feedback analysis 定義為 key decision/action 前寫下預期、之後比較實際結果。原文以 9 或 12 個月為例；本片沒有把 9／12 個月當成硬性規則，只保留「之後回看」。 |
| 多筆紀錄可用來辨識反覆出現的能力線索 | **可採用，但屬方法化表述** | Drucker 原文說持續實行後可看見 strengths、能力與習慣；本片把它轉成「多筆紀錄找模式」，是忠於原理的創作改寫，不宣稱一次結果就能判定強項。 |
| 只靠感覺做自我評估可能失準 | **可採用** | Karpen (2018) 的開放取得回顧整理自我評估與外部標準常只有弱到中度關聯，並指出自我知識容易受無意識偏誤影響。這不是說每個人都一定高估自己，也不是本片的個人診斷。 |
| 使用個人強項與工作表現、員工福祉呈正向關聯 | **可採用，但不等於因果保證** | Rudolph, Friedrich, Koziel et al. (2025) 的 meta-analysis 報告 strengths use 與 work performance、worker wellbeing 的正向關聯（ρ = .421、.621），且未支持「strengths overuse」的非線性關係。這項研究不是 Drucker feedback analysis 的直接驗證；本片不放效應量、不保證收入或成功。 |
| 不要被一次成功／失敗定型 | **編輯防誤導句** | 是本片為避免過度解讀單次結果而加的操作護欄，不是研究中的固定次數規則，也不宣稱每次結果都能排除運氣與情境。 |
| 「哈佛追蹤 2,000 人、優勢投入者收入增速 3 倍」 | **刪除，不採用** | 已用中英文變體與 Harvard／Drucker／strengths／income 等關鍵字檢索，未找到可核對的原始研究、作者、年份、研究設計與數據頁碼；搜尋摘要與二手貼文不足以支撐。成品不使用 2,000 人、10 年、80%、3 倍收入等數字或歸因。 |

## 內容邊界

- 本片是觀念與自我觀察練習，不是心理測驗、職涯診斷或收入承諾。
- `strengths use` 研究與 Drucker 的 feedback analysis 不是同一個研究構念；影片把它們並列為「原始方法＋研究補充」，沒有宣稱後者證明前者。
- 「先找強項」不等於永遠不補短板。Drucker 原文也要求補足實現強項所需的知識、技能，並修正妨礙績效的壞習慣。
- 本專案不出現保險商品或公司名稱，也不含推銷 CTA。
- 影片中不使用未查證的 Harvard、2,000 人、10 年、80%、3 倍收入說法。

## v2 重跑方式（Windows）

本次保留原 17 句旁白與來源範圍，只改分鏡、畫面文字、輪播與結尾停留時間。示例中的「教工具／交接工作／先畫步驟圖」是編輯示例，不是個案證據，也不推論因果；三筆紀錄不是能力認定門檻。既有來源與查證表沿用基準版，本輪依使用者限制未另行瀏覽或重新查核外部來源。

使用既有模型目錄，不需下載新模型：

~~~powershell
uv venv --python 3.11 build/venv
uv pip install --python build/venv/Scripts/python.exe -r requirements-render.txt
npm install
.\make.ps1
~~~

- make.ps1 自動設定 MODELS_DIR=C:/Users/Public/hermes_models、CHROME_PATH=C:/Program Files/Google/Chrome/Application/chrome.exe、PYTHONUTF8=1。
- 需要 PATH 可找到 Node、uv 與 ffprobe。已有本機套件時不需重裝。
- 只改畫面且已有同一份旁白／時間軸時，可用 .\make.ps1 -ReuseVoice。改過 script 的文字或時間設定時不可省略 TTS 步驟。
- 原 make.sh 保留；字幕現在由 events 步驟一併輸出瀏覽器量測的斷行，SRT 不再另猜行寬。
- build/ 不進 Git；output/qa/timeline.json 保存本次實際旁白時間。TTS 套件／版本不同可能有毫秒差異，必須整套重跑。
- 瀏覽器 PNG 用於輪播；影片每幀以品質 95 的 JPEG 傳給 ffmpeg，再編碼 H.264。紙張／字型／手繪路徑仍來自原專案，未引入外部圖片。
- render/lib.js 保留原工具庫，未用到的其他題材元件不會出現在本片。
- 原檔已備份於 institution/_backups/strengths-feedback-analysis-20260928，Git 基準也可還原。

### QA 邊界與本次檢查方法

- 原 QA 把6個相同影格（0.2秒）算凍結；原版持續線條抖動又會避開這個判準。v2 移除裝飾性抖動，改為超過4秒的靜止警示，另以每幕兩段事件前後抽幀確認內容改變。原有黑白區、均勻畫面、幀差門檻不放寬。
- output/qa/motion.json 的像素差只代表畫面有變，不等於動作有意義。動作語意另根據事件圖逐張審查，結果寫在 REVISION_CHANGELOG.md。
- output/audit_before/ 是原MP4的逐秒證據；output/review_seconds/ 是v2成品的逐秒證據。每張 contact_XX.png 都來自實際解碼，不是只用瀏覽器預覽代替成品。
- 一秒抽樣圖使用1fps抽樣桶；events_*.png與transitions.png標示以30fps四捨五入的實際擷取時間。仍不是宣稱已肉眼看過全部1,597幀。
